# Agent 协作规范

适用于《照影廊》当前仓库中的多人开发。当前开发入口是 `v2/`，根目录与 `first-cut/` 保留历史原型。每轮以用户最新指示和远端代码为准。

## 职责与交接

| 职责 | 主要工作 | 交接给 |
| --- | --- | --- |
| Codex · 美术与交付验证 | 生成和筛选母图、维护画风与来源、接入现有导入管线、对照运行图与清单、准备可复玩的评审材料、复测和归档 | 专门的画审检验成品。涉及玩法、通用 UI、输入或数据结构的发现交给对应负责人 |
| 玩法与数值 | 战斗和事件规则、货物经济、构筑、模拟策略和同签对照 | 工程负责人实现或复核。需要新图时提供玩法用途、姿态和替换范围 |
| 工程与界面 | 规则实现、存档、输入、渲染、通用 UI、构建和自动化 | 协商共享入口与资产接口，反馈给需求负责人和复测人 |
| 独立画审、玩法复审 | 用可复现的包、种子、界面和输入记录检查实际结果，标注缺陷、严重度及复验结果 | 原负责人修正，同一评审核对退回项。评审人没有被分配到任务时标为待安排 |

职责是默认分工。任务清单中的负责人须由实际执行者认领。评审结论用于验收，发布授权由该任务获得的用户授权与仓库规则决定。

## 开始工作

1. 读取[协作任务](协作任务.md)及相关日志。先执行 `git status --short --branch` 和 `git fetch origin`，核对本地工作和远端提交。将并行工作放在各自的分支或工作树。
2. 在任务清单登记任务 ID、真实负责人、状态、工作树或分支、预计触及的共享路径、验收办法。认领记录先同步到远端，方便其他协作者避开同一范围。同一文件的多项改动由相关负责人协商顺序或明确分工。
3. 台账是公开的协作记录。它有传播延迟。两人同时认领或发现同一文件已有未归属的改动时，保留现状，协调后再开始冲突范围内的工作。可以继续做互不冲突的部分。
4. 制作中遇到别的模块问题，在该任务的「依赖／交接」里写清种子、输入、期望、实际、相关路径和需要谁决定。涉及需求变化时更新任务边界，交接完成后由新的负责人更新状态。

## 纠错与验收

- 使用 `待认领 → 进行中 → 待复审 → 已合入`。发现重大回归标 `待修正`，因明确依赖暂停则标 `受阻` 并写明恢复条件。复审中的负责人保留对文件范围的认领。
- 复审写清楚版本或提交、测试入口、可复现输入和证据。美术核对母图、构图、透明边、角色肢体、动作衔接及游戏实际大小。若用开发入口指定遭遇，证据注明它与随机流程的区别。玩法复审明确玩家在哪一步改变计划，区分模拟、代理试玩与真人反馈。
- 阻断问题由原负责人修正并送复验。修复涉及另一组的共享文件时先在任务清单建立交接。最终日志列出通过、未验证和仍存在的限制。
- 美术任务用 [v2 美术需求](../v2/docs/美术需求.md) 的资源 ID。保存 PNG、WebP、提示词、来源和哈希。尽量只导出本批文件，更新美术清单。至少检查桌面和 390 宽模拟；按风险补姿态、怪物落点和交易状态。

## 文档与素材的关系

1. **入口先说结论。** 从 [开发导航](开发导航.md) 进入。索引说明版本及资料的入口。任务日志开头用几句话说明哪项行为变了、验收到哪一步，再链接设计、源码与证据。图组、长提示、逐帧数据放在任务目录中，从日志点进去查看。
2. **引用现有 ID。** 任务 ID 以 [协作任务](协作任务.md) 为准。游戏实体使用 `enemy:bell`、`event:scavenge`、`floor:3` 等带类型的 ID，另有 `goods`、`card`、`relic`。还没有代码 ID 的跨文档机制先在 [资料索引](资料索引.json) 加入简短的定义入口。显示名改动时沿用原 ID。
3. **记录出处和替代关系。** 每个新增母图以游戏使用的素材 ID 入库，[导出记录](../v2/art/exports.json) 提供文件和哈希，[美术清单](../v2/docs/美术清单.json) 给出实际用途。美术日志链接提示词、原图或上游来源，用已有 [许可说明](素材与许可.md)。规则文档改版时链回原文，注明哪段由新版取代。历史原型仍被导出的素材从导出器查源路径。
4. **给新日志附任务关系。** 将下面的注释放在标题下。证据使用相对日志的仓库路径，基线填测量或制作所用的 Git 提交。任务没有对应素材或依赖时可以用空数组。任务状态与负责人留在任务清单，校验值留在导出记录。文件移位先更新被引用的路径。

```html
<!-- task-trace
{
  "schemaVersion": 1,
  "taskId": "ART-007C",
  "entities": ["enemy:bell", "floor:3", "mechanic:turn-combat"],
  "assets": ["bell-heavy", "bell-heavy-attack", "bell-heavy-hurt"],
  "dependsOn": ["ART-007"],
  "evidence": ["media/ART-007C/独立画审.md"],
  "sourceRevision": "66a116a"
}
-->
```

发布前在 `v2/` 运行 `npm run docs:check -- --base origin/main`，检查仓库资料归属、任务与实体 ID、证据路径及素材哈希。旧资料从历史入口按目录查找，逐份回填时使用已经能核实的关系。

## 提交与同步

1. 收口前检查 `git diff --check`、运行对应验证，逐文件核对暂存区。把任务状态、证据和限制写进[开发日志](dev-log/README.md)。共享台账只更新受影响的条目。
2. 提交自有变更后再执行 `git fetch origin`、`git rebase origin/main`，检查合并后的差异。远端有相关改动时重跑受影响的检查。冲突仅在确认双方意图后解决，无法安全合并时在台账记下阻断。
3. 按该任务获得的用户授权和仓库规则选择推送目标，执行普通快进推送。推送被拒绝时重新 fetch/rebase。仓库保护或用户要求 PR 时走对应流程。强制推送、覆写他人变更、公开发布候选及外部部署需各自符合用户授权。
4. 推送后比较本地提交与远端分支，台账只在验收通过、内容已进入共享分支时宣称「已合入」。如完成提交同时携带台账状态，推送失败要保留本地提交并在恢复后核对远端状态。
