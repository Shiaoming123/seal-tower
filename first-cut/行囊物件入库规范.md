# 行囊物件入库规范

适用于《照影廊·一印两价》4 列 × 3 行的初始行囊与装衬布后的 4 列 × 4 行行囊。入库同时满足三项条件：玩家能从实物看出占位，规则认可同一组格子，该物件占去的空间配得上它在一局中的用途。设计者登记物件，美术准备原图，程序出具量测与反例，另一位评审在最终试玩包上签核。

## 1. 先确定物件的用途和收纳姿态

为每件物品写下名称、交易或战斗作用、装备位、取得／交出时点、预计占格与想给玩家的取舍。例如，买下新剑会把照影剑放入囊中，同时要为下一只墨蠹的掉落保留空间。按物件携带时的实体轮廓选形，剑刃要有连续长度，弯壳可以让出一角，小铃能塞进空隙。药耗、已装备的法宝和袋内货物各自记账。相同种类可以有不同轮廓。

优先找现成透明原图。先用原比例调整朝向和整体尺度，看刃尖、护手、钩口、壳弯、佩结是否自然覆盖目标格。原图合适就直接复用。需要折叠、包裹或换视角时，为同一物件制作明确的收纳姿态，校对外形、材质、缺角等识别特征。桌面陈列可以使用不同视角；验货页保留清楚的整物。渲染时整张透明图一次画完，不沿格线剪切。投影、光晕和游标在独立层绘制，勿将大片地面或阴影烘进透明原图。

## 2. 登记唯一的格形和姿态

在 [game.js](../game.js) 的 `bagLayout` 登记物件，在 [sprite-bank.js](sprite-bank.js) 登记可离线载入的透明精灵。运行时规则、预览、落位、像素检查都按同一目录取数。

| 字段 | 定义 |
| --- | --- |
| `rows` | 从上到下，`x` 表示实占，`.` 表示让出的格。形状四邻接连通，四条外边都至少接触一个实占格。 |
| `sprite` | 可溯源的完整透明图。图源与摆放姿态一起接受评审。 |
| `degrees, span` | 初始朝向与缩放。正角度顺时针。原图较长一边缩放到 `span` 格，斜向原图转正后的可见长度另行测量。 |
| `cx, cy` | 原图中心放置点，以格为单位，从初始外接矩形左上角量起。 |
| `minCell` | 每个实占格内，透明度加权的最低覆盖率。按物件最细的必要部分预先登记；当期通用下限为 6%。 |

运行时存储物件 ID、外接矩形左上角和四分之一圈转数。所有动作使用 `Tower.footprint`、`Tower.canArrange` 和 `Tower.arrange`。例如，墨蠹壳的 `[".x","xx"]` 占三格。把壳放在坐标 (1,1)，铜铃也可以放在 (1,1)；(2,1) 已被壳占用。鼠标拖动或触屏选格都必须保留这个结果。同种物可有多叠。每叠用独立实例 ID 加数量定位；移动、拆叠、按份出售和确认弃物都指向该实例。灯灰与封蜡绢每叠最多三份。数量角标独立于原图绘制，像素轮廓检验只比较实物图层。衬布在购买时开底部第四行，原物坐标保持。

## 3. 程序验收

从项目根目录，在有 Python 3、Node、Playwright 以及可启动 Chrome 或 Chromium 的环境中运行。游戏本身可以离线游玩。带验收参数的构建在下列检查通过后才替换试玩文件。

```bash
python first-cut/build_offline.py --verify-inventory 'evidence/展柜与行囊/占格像素质检'
```

| 检查 | 可观测的通过条件 |
| --- | --- |
| 目录和规则 | 所有可携带物都有完整登记。独立坐标公式与引擎四向结果一致。测试空位、边界、邻物、凹角与同位操作。成功移动只改装载位置，拒绝时原状态完整。 |
| 原图对照 | 用每格 96 像素、四周额外留 192 像素的画布独立变换原图，再与游戏真实绘制逐像素比较。分别从原图和成品的每一格读取 alpha，覆盖率达到 6% 就认作一格材料。输出设计声明、原图读数、成品读数三组独立格图，三者须一致。原始 alpha 质量保留率 ≥99.3%，归一化预乘 RGB 误差 ≤2.5%。 |
| 格形边界 | 外接框外、框内让出的格，分别最多占原图 alpha 质量的 0.2%。两者在 alpha ≥32/255 时都须为零像素。每个实占格达到登记覆盖率，每条相邻实占格边界至少有 4 个两侧都可见的采样点。 |
| 轮廓和旋转 | 照影剑、饮棘钩与守阙剑的可见长轴至少 2.67 格；四次转向回到初态时，逻辑占位与实际图像像素完全一致。 |
| 拼放和反例 | 在真实战利品流程中将完整铜铃放入墨壳凹角，可见像素交叠为零；相邻已占格必须拒绝。故意把长剑缩成一格，必须报长度、逐格覆盖和跨界断开；故意平移墨壳，必须报凹角侵入和明显越格。 |
| 交易 | 另跑经济回归，验证换装后旧物入囊、满包拒购、未收战利管理，以及资源、伤害和寄单规则。 |

## 4. 判断这个形状是否值得占这些空间

容量检验分别枚举 12 格的全部 4,096 种、16 格的全部 65,536 种空位分布。对每种形状，允许四向旋转，在其余货物不动的前提下，记录每个剩余面积上有多少种布局能放入它。由此可比较面积一样、整理难度不同的物件。

| 物件 | 恰好剩 3 格，可放布局 / 全部布局 | 剩 6 格，可放布局 / 全部布局 |
| --- | ---: | ---: |
| 照影剑，直三格 | 10 / 220 | 618 / 924 |
| 墨蠹壳，L 形三格 | 24 / 220 | 803 / 924 |
| 护心镜，直两格 | 136 / 220 | 922 / 924 |
| 旧铜铃，单格 | 220 / 220 | 924 / 924 |

设计者据此设置有意义的机会成本。示例中携带备用长剑对连续空间的要求高，而价值 2 石的弯壳较容易安放。上述比例等权枚举几何布局；真实玩家可能整理、换装或偏爱某个角落。调价、改格或扩容前，应在相同掉落和初始资源下玩对照路线，记录实际拒购、放弃、整理次数及关后收益。要判定玩家是否享受整理，需要另做玩家试玩。

## 5. 画面复核与退回

独立评审先看透明原图的轮廓、比例、残边、光向与材质，再看桌面实机、390 像素触屏视口、未付款验货和真正的行囊。至少逐件点选长剑、L 形壳、嵌入的铜铃，比较高亮的格和说明，再看合法／非法移位的投影、落位与取消。手机下要分得清物件朝向和保留的凹角。

每轮保留四向拼图、量测 JSON、反例图、真实桌面／手机截图、可重放的操作记录和对应试玩 HTML 的 SHA-256。出现错误，定位到原图、登记姿态、碰撞逻辑、绘制或界面层分别修正，重跑有关检查，并交由独立评审复看。更换透明图、收纳姿态或渲染代码必须重新核对量测和实机。素材本身做坏却满足格形时，画审仍可退回。

在上述构建之后，再从根目录执行 `node first-cut/check-inventory-play.cjs`。这会用同一份 HTML 走完桌面鼠标和 390 像素离线触屏模拟的摆放与交易，截图及操作记录默认写入 `evidence/展柜与行囊/实操`。交付时把轨迹中的包指纹与画审报告对照。

### 押运行商与版本回放

商号初次登记在旺市出售封蜡绢并结清当局之后。旧的寄单单次领取、商号状态、正常开局的灵石和气血分别复验。押运的托箱由商号借给镖车；沿驿买卖和支道换来的私货必须写入同一份锦囊。灰换壳要按交出一份灰后的真实形状复算空间。

以下命令从项目根目录运行。第一条打出独立候选、保留当前试玩文件。第二条枚举 256 签的七种押运策略，第三条使用完整浏览器按常速从第一剑行车至末市。录视频时允许捕获本轮游戏标签音频的测试环境，并安装 FFmpeg。最后一条在 390 像素离线触屏模拟走同一条支道交易线，使用游戏自带的催马功能。输出目录可换为新的核验目录。



~~~bash
python first-cut/build_offline.py --verify-inventory [本机路径略] --output [本机路径略]/local-run.html
node first-cut/escort-balance.cjs --out [本机路径略]/escort-simulation.json
node first-cut/check-escort-play.cjs --bundle [本机路径略]/local-run.html --flow caravan --video --out [本机路径略]
node first-cut/check-escort-play.cjs --bundle [本机路径略]/local-run.html --flow caravan --quick --out [本机路径略]
~~~

检查报告中的候选 SHA-256、交易份数、沿途货差、入镖前私货卖款、实交箱数与末市总账。行驶总时长含做出选择后车轮驶向路标的时间。后台和手札暂停另列，催马局及录像节选时长另计。
